# Security and trust

## What exists today

Maestro is currently a local editor with no network code and no plugin system. Its subprocesses are the clipboard helpers, `git`, the language servers, and the coding agents and verification commands the user starts from the agent panel, all described below. The automation API (below) listens only on a Unix socket, and only when started with `--listen`.

- Files are written atomically through a temp file in the same directory, created with `create_new` so an existing file of that name is never clobbered, and removed on failure only if this save created it. When an existing file is replaced, the temp file is created owner-only (0600) and gets the original's permissions just before the rename, so private contents are never briefly readable by others. Symlinks, including dangling ones, are followed so the link survives.
- Before overwriting, a save compares the file's metadata, identity (device and inode on Unix) and a hash of its bytes with what was last read or written. Any difference refuses the save until the user picks `:w!` or `:reload`.
- Binary files and files that are not valid in a supported encoding open read-only, so saving cannot rewrite bytes the user never saw.
- Recovery files contain file contents. The directory is created with mode 0700 and each file with mode 0600 on Unix. Unnamed buffers are not journaled. Each editor session writes and deletes only its own recovery files; another session's files are removed only by `:recover` (after copying the text into this session's journal) or `:recover-discard`.
- Sessions (`sessions/<hash of the directory>.toml`) and the recent-files list (`recent.toml`) in the state directory hold file paths and cursor positions, not contents. They are written atomically with mode 0600; the directories are created with, or tightened to, mode 0700, and the temp file is created exclusively so a file or symlink already at its name is never written through. `--clean` reads and writes neither; `restore-session = false` turns sessions off.
- Agent records (`agents/<hash of the main worktree path>.json` in the state directory) are written the same way: 0600, atomically, in a directory created or tightened to 0700. They hold task text, the task contract (whose verification command `t` runs), review comments, history, error messages, the verification command line and the last 100 output lines of each saved test run, which can contain whatever the tests printed. They never hold a provider's arguments or environment (where API keys usually are), the ACP transcript or terminal output; the history names the program that was started. `--clean`, headless runs and `restore-session = false` neither read nor write them. A file that is not a regular file, larger than 64 MiB, not valid, of another version or written for another repository is reported and left in place, and that repository's records are not saved in that session. Before each save Maestro compares the file with what it last read or wrote: records another Maestro added are kept, and a file that became unusable is left alone and saving stops. Another program writing in the moment between that check and the rename can still be overwritten. Records are checked before use: a record must name a known provider kind, an absolute worktree path, the same main worktree, a `maestro/` branch, a hexadecimal base commit and ids in range, or the whole file is refused. The record's path is not trusted beyond that: before tests or a relaunch, the worktree's `.git` file and `HEAD` must show a worktree of the same repository on the recorded branch, and before dropping a file, committing or integrating, Git must show the same.
- Relaunching an agent from a record runs the provider of that name and kind from the current config, never a command read from the state file.
- A record does not prove that no process runs. Records saved by a Maestro that is still running in the same repository load as not running, and relaunching or archiving one acts under that editor's agent. Before archiving, Maestro checks that Git lists the worktree on the branch the record names; a worktree switched to other work is not removed.
- The file finder and workspace search only read files; they do not follow symlinked directories, and they skip anything the repository's ignore files exclude. The preview opens regular files only, so a FIFO in the tree cannot hang the editor.
- Control characters are never written to the terminal from a cell: the renderer shows them as `?`, so a file name or file text containing an escape sequence cannot drive the terminal.
- Config is parsed with `deny_unknown_fields`, and key bindings that name unknown commands are rejected at startup.
- Clipboard: `pbcopy`/`pbpaste`, `wl-copy`/`wl-paste`, `xclip` or `xsel` are run by name from `PATH` with fixed arguments. The text goes over stdin; it is never put on a command line. Without them, copying uses the OSC 52 terminal escape.
- Git: `maestro-git` runs `git` from `PATH` with argument vectors, never a shell. Paths are separate arguments with `GIT_LITERAL_PATHSPECS=1`; revisions starting with `-` are refused and new branch names are checked with `git check-ref-format`. Read-only calls (status, diffs, base texts) set `GIT_OPTIONAL_LOCKS=0` and `GIT_NO_LAZY_FETCH=1`. `GIT_TERMINAL_PROMPT=0` stops terminal password prompts; a configured askpass or credential helper can still run, and calls have no timeout.
- Removing a worktree refuses, unless the caller passes `force`, when `git status` reports uncommitted changes or untracked files, or when its `HEAD` has commits that are ahead of its upstream or (without one) on no other branch or remote-tracking branch. That last check also runs for a worktree whose directory is gone. The main and locked worktrees are never removed, even with `force`. Not detected: edits to files marked `assume-unchanged` or `skip-worktree`, and ignored files, which are deleted with the directory as `git worktree remove` does.
- Language servers are run by name from the user's config (`[language-server.<lang>]` in `config.toml`) or from built-in defaults (`rust-analyzer`, `pyright-langserver` or `pylsp`, `typescript-language-server`, `clangd`). Maestro never reads server names, commands or arguments from files inside a repository, so opening a file cannot choose what runs. The program is looked up in the absolute entries of `PATH`, or, if the config names a path, resolved to an absolute path against the directory Maestro started in, so the workspace root (the server's working directory) never changes which file runs. It is started with fixed arguments, the workspace root as its working directory, and the editor's environment. A server that is not installed is reported once and skipped. One that crashes stays stopped until `:lsp-restart`, so a broken server cannot restart in a loop.
- Language servers only start in the interactive terminal editor. `maestro --headless`, `--first-frame-only`, and editors built for tests leave `lsp.enabled` off, so an unattended run never starts a program that can execute repository code. Headless runs also read and write no session or recent-files state.
- A server sees the full text of every open file in its language, plus whatever it reads from the workspace itself. Its stderr and log messages are kept in memory (the last 2,000 lines per server, shown by `:lsp-log`); they are never written to the terminal or to disk. Messages over 64 MiB are refused.
- Replies are applied on the editor thread. A definition, references or hover reply is dropped if any open buffer changed while it was being computed. Files a reply points into are read on a background thread, and only if they are regular files of at most 16 MiB; the file type is checked again just before the editor opens it. A file swapped for a FIFO in the instant between that check and the open could still block the editor; nothing else in a reply can. A reply that arrives while a prompt or picker is open, or in insert mode, is dropped so it cannot act on input meant for something else. Language servers cannot edit buffers in this version (no code actions, renames or formatting).
- No `unsafe` code; the workspace forbids it.

## Automation API

`maestro --headless` talks only over its own stdin and stdout, so whoever started the process is the only client. `maestro --listen` serves a Unix socket while the editor runs. The trust model for the socket:

- It is local only. There is no TCP listener.
- The socket file has mode 0600 and the default location is `$XDG_RUNTIME_DIR/maestro/<pid>.sock`, a per-user directory. A missing parent directory is created with mode 0700. The socket is bound inside a fresh 0700 directory, set to 0600 and then hard-linked into place, so it never exists with the umask's looser permissions. Linking fails if anything appeared at the path in the meantime, so a file or another editor's socket there is never replaced. There is no fallback to `/tmp`.
- File permissions are the only access control. There is no token or other authentication, so any process running as the same user can connect and do anything the API allows, including editing and saving any open file. This is the same trust a process running as the user already has over the user's files.
- Peer credentials are not checked. On Linux only the owner (and root) can connect to a 0600 socket anyway.
- `document.apply_edit` checks the document version and refuses a stale edit without changing anything. It and approved proposals are the only version-checked ways to change text. A client can also change text with `command.run` (for example `delete_selection`) or `editor.execute` (for example `:%s`); those act on the editor's current state with no version check and are not recorded in `document.history`. All three apply immediately. A client that wants the person at the editor to decide uses `proposal.create` (below); nothing forces a client to, since `document.apply_edit` remains available to any client.
- The review shows exact bytes: a `\r` added or removed before a newline shows as a changed line, and a line cut off at the review's right edge is marked with `>` (the approval dialog counts such lines; `h` and `l` scroll to them). Dialog text is wrapped by screen cells, so wide characters cannot push the end of the command off the dialog.
- Proposals (`proposal.create`) change nothing until the person at the editor approves one in the review overlay; a key press in the editor is the only way to approve. Keys replayed by a macro or by `.` are ignored in the overlay, so a recorded approval cannot approve a later proposal unseen, and the API has no request that types keys. A client can queue up to 100 pending proposals, withdraw the pending proposals its own connection created (any other connection's withdraw is refused with -32020; the server numbers each connection at `initialize`, because actor names are whatever a client sends), and read every proposal's status and history. This keeps one client from taking back another's proposal by mistake or on purpose; it is not a boundary between users, since only the user who owns the socket can connect at all. It cannot approve, reject or apply one.
- A proposal's verification command comes from the client. It runs only after the user approves that proposal, in a dialog that shows the whole command, word by word and shell-quoted, with the directory it runs in, and says that the file is saved first. Control characters and invisible or direction-changing Unicode characters in the command are shown escaped (`$'...'` with `\n`, `\u202E` and so on), so a newline in an `sh -c` script or a bidirectional override cannot hide part of it. The program is quoted more strictly than the arguments: a name containing `=` (which a shell would read as an assignment) or a reserved word is quoted, and every non-ASCII character in it is escaped, so a look-alike name shows as different. One gap remains: Maestro runs the program found on `PATH`, while a shell given the name of a builtin (`exec`, `cd`) would run the builtin. A dialog that does not fit the window cannot be accepted. The command then runs as the user, with the editor's full environment, in the editor's working directory, with no sandbox and no time limit; `c` in the review and quitting the editor kill its process group while the command runs. When the command exits, processes it left running in its process group get SIGHUP, then SIGKILL once the group is otherwise empty or after 200 ms, before the result is reported; a process that moved to another process group or session (`setsid`, a daemon) is not reached and keeps running. Approving a proposal is approving that command: read it.
- Approving applies the proposal only if the document is still at the proposal's base version (`Document::apply_at_version`) and still has the path the proposal was made for (`:w other` renames a buffer without changing its version); otherwise it is refused as stale and nothing is saved or run. With a verification command the document is saved before the command runs. If the user had unsaved edits in that buffer, saving writes them too; the dialog says so first.
- Headless runs refuse `proposal.create`: nobody is there to approve. There is no option, for the client or on the command line, that approves proposals without a person.
- The actor name and agent id on a proposal are what the client sent, as with `document.apply_edit`. `decided_by` records the login name from `$USER` or `$LOGNAME`, which the environment controls.
- `document.open` and `document.save` accept any path the user can read or write, including paths outside the workspace root. A client can therefore read and overwrite files outside the project. A workspace boundary is planned with the permission system.
- The edit log (`document.history`) records the actor string the client sent. The server does not verify it; any client can claim any actor name.
- Writes to a client happen on the editor's thread. Each message has a 2-second deadline in total; a client that misses it is disconnected. A client that stops reading can therefore freeze the editor for up to 2 seconds per message, and several such clients add up.
- A request line longer than 64 MiB gets an error and the connection is closed. Each connection may have at most 32 requests queued for the editor; past that its reader stops reading until the editor catches up.
- `document.open` refuses paths that exist and are not regular files (FIFOs, sockets, devices), because reading one could block the editor thread with no way to cancel.
- The socket is removed when the editor exits normally. After a crash it stays behind; the next `--listen` on that path replaces it only if connecting is refused (nobody listening). Any other connection error is reported and the file is left alone. Between that check and the removal there is a small window in which another process could put a new socket there and have it removed.
- Windows has no socket transport yet; `--listen` is refused there.

## Coding agents

The agent panel (`space a`) runs coding agents. What they can and cannot do:

- An agent is a program from the user's config (`[agents.provider.<name>]`) or a built-in provider found on `PATH` (`gemini`, `opencode`, `claude`, `codex`). Like language servers, providers are never read from files inside a repository. Nothing starts until the user types a task and picks a provider.
- The agent runs as the user, with the editor's full environment (API keys and tokens in it included) and its worktree as the working directory. A Git worktree isolates source, not privileges: the agent can read, write and run anything the user can, anywhere on the machine, and reach the network. There is no OS sandbox.
- For ACP agents, file reads and writes the agent asks Maestro to do (`fs/read_text_file`, `fs/write_text_file`) are confined to the worktree by path checks: paths outside it, symlinks out of it and the `.git` directory are refused. That confinement covers only those requests. The agent's own tools (its shell, its own file writes) do not go through Maestro and are not confined at all. The path checks also have a race: a process swapping a checked directory for a symlink at the right moment can redirect a write.
- Permission requests from an ACP agent are shown in the panel. Granting one needs a second key in a confirmation dialog; nothing is granted automatically. An agent that does not ask (most terminal agents, and any agent using its own tools) is not stopped by this.
- A terminal agent's task text is passed as an argument (one argument per `{task}`, no shell involved) or typed into its terminal. A provider configured as `sh -c "... {task}"` would hand the task text to a shell; do not configure one that way.
- Agent output is untrusted. Maestro moves an agent's work into the main worktree only through integration, which the user starts and confirms. That is not a boundary on the agent: its own tools can write into the main worktree, or anywhere else, at any time, and rejecting it does not undo that. `maestro-git` refuses to integrate into a dirty, detached or mid-operation worktree, refuses on conflicts found by a dry run, and aborts what it started if git fails. Before committing anything, Maestro checks again that both worktrees still exist and are on the branches the dialog named, that the main worktree is clean, and that the agent's starting commit is on the target branch (so nothing the review did not show comes along); it also refuses while a buffer in either worktree has unsaved edits. Like `git merge`, integration can overwrite ignored files in the main worktree that the agent's branch adds as tracked files.
- Integration runs the repository's Git hooks (`commit_all` and the merge or cherry-pick commit), and the agent controls the files in its worktree, so integrating runs hooks over files the agent wrote.
- Archiving removes the worktree only when `maestro-git` finds no uncommitted or untracked files, and no commits ahead of its upstream or (without one) on no other branch. Ignored files (build output, `.env`) are not checked: they are deleted with the worktree on the first confirmation, as `git worktree remove` does, and both dialogs say so. Forcing needs a second confirmation that lists the files it deletes and any commits on a detached `HEAD` that become unreachable. The agent's branch is always kept.
- Rejecting, archiving and quitting stop the agent. ACP agents run in their own process group, which is killed. Terminal agents' process groups get SIGHUP and, 200 ms later, SIGKILL, so descendants end too unless they moved to another process group or session (a daemon does); archiving waits up to three seconds for the program to exit before removing anything, and quitting waits up to one second. Test runs are killed by process group, and what a test run leaves in its group when it exits is ended the same way as for a proposal's verification command. Maestro never signals a process group whose id could have been reused: each command's group is led by a placeholder process (`cat` on a pipe only Maestro holds), which is reaped only after the group's last signal. `:q` and `:qa` refuse while Git work for an agent is running (a worktree being made, an integration, an archive), and ask before stopping running agents. The automation API's `editor.quit` refuses while Git work runs, and while agents or tests run unless `force` is passed, which stops them first.
- Terminal output is drawn cell by cell through the same renderer as files, so control characters show as `?` and cannot reach the user's terminal.
- Verification runs the task contract's command when it has one, else `[agents] test-command`, or `cargo test` when the worktree has a `Cargo.toml`. `cargo test` builds and runs code from the worktree, which the agent wrote.

### Task contracts: what they enforce and what they only ask

A contract (see `docs/agent-model.md`) is a request to the agent. Sending it does not confine anything: the agent runs as the user with the same powers as without one.

What Maestro enforces:

- ACP file writes the agent asks Maestro to make (`fs/write_text_file`) outside the allowed paths, or in a forbidden one, are refused. The check runs after the worktree confinement, on the path the write would actually reach (symlinks resolved), and before any directory is created. It is the same path check as the confinement, with the same race: a process swapping a checked directory for a symlink at the right moment can redirect a write.
- Integration does not take in a changed file outside the contract unless the user presses `O` in a dialog that names every such file (`y` is refused; a dialog too long for the window cannot be accepted). The list comes from Git when the dialog opens and covers both the net diff and every commit on the agent's branch, so a file changed and changed back by commits (which a cherry-pick would apply one by one) is listed. After the agent's work is committed and before the merge, the branch must hold exactly the files the dialog was computed on and nothing outside the contract that the dialog did not name; otherwise nothing is integrated. A process committing to the agent's branch in the moment between that check and the merge is not stopped. After the merge Maestro compares the target branch before and after against the contract and reports any file outside it that the dialog did not name as an error, but by then it is on the target branch. The review marks the same files. When Maestro made the commit, its message names the files `O` let in; the agent's history names them either way.

What it does not enforce: anything the agent does with its own tools (a shell, its own file writes, any terminal agent), reads of any path, the acceptance criteria, or what the agent sends to its model provider. A file outside the contract can still land in the worktree; it is shown, not prevented.

Patterns match case-sensitively. On a case-insensitive file system (macOS by default), a path spelled with other letter case names the same file but may not match the same patterns, so a forbidden pattern is not a reliable block there. A contract file is read only when the user names it with `@contract`, and only a regular file of at most 64 KiB, checked on the path and again on the opened file, and read with that limit; it is read on the editor thread, so a FIFO swapped in between the check and the open can still block the editor. It is parsed as data with unknown keys refused, and its patterns must stay inside the repository (no absolute paths, `..` or `!`). Its verification command runs only when the user presses `t`, as the user, in the worktree, with the editor's environment and no sandbox, like `[agents] test-command`. The dialog shown before the task starts lists the whole contract, with the command quoted word by word and control and direction-changing characters escaped, so a file cannot hide part of it. Contracts are saved in the agent records and checked again when read; a saved verification command runs on `t` after a restart. The records file is the user's own (0600, in the state directory).

### Conflict detection

To compare agents' uncommitted work, Maestro writes a snapshot of each overlapping agent's worktree as Git objects: `git add` into a temporary copy of the worktree's index (outside the repository, in the system temp directory, created exclusively), then `write-tree` and `commit-tree` with a fixed author. That puts the contents of the agent's files, untracked ones included (ignored ones not), into the repository's object store as unreferenced objects; no ref, branch, reflog, index or working file changes, and `git gc` drops them later. `git add` applies the repository's clean filters (`.gitattributes` with `filter.<name>.clean` in Git config), which can run programs named in the user's or repository's Git config, as `git status` can (see Known gaps). The integrate dialog's dry run writes one more unreferenced merge commit the same way. Merge dry runs use `git merge-tree`, which changes no ref, index or working file; it does run the merge machinery, so a custom merge driver named in Git config (`merge.<name>.driver`, selected by `.gitattributes`) runs for files it applies to, in the background, before the user has decided anything. Integration itself runs the same drivers.

## Trust boundaries for what comes next

- Repository contents are untrusted. Maestro will not run tasks, hooks or language servers named by a repository without the user approving them for that workspace. Note that a trusted server can still act on repository contents: `rust-analyzer`, for example, runs `cargo` and build scripts from the project it indexes. Opening a Rust file from an untrusted repository with the default config runs that repository's build scripts. Set `enabled = false` under `[language-server.rust]` to avoid it.
- Agent output is untrusted. Agents started from the panel write files in their own worktree, and the user integrates them with explicit approval (see Coding agents). An automation client (which can be an agent) can propose edits to open buffers with `proposal.create`; they are checked against document versions and wait for the user. The same client can also call `document.apply_edit`, which does not wait: proposals are a way for a cooperative client to ask, not a boundary against a hostile one, since any process that can reach the socket is trusted as the user.
- Planned: an OS sandbox for agent processes, and not forwarding environment variables to agents by default. Neither exists yet; today agents get the editor's whole environment.
- Project contents go to a model provider only through an agent the user started from the panel. What that agent sends is up to the agent program; Maestro does not filter it.

## Known gaps

- `git` runs with the user's configuration, including the repository's own `.git/config`. A repository unpacked from an archive with a hostile `.git/config` could name a command in `core.fsmonitor`, which `git status` (run for gutter signs and the status picker) would execute. `git worktree add` runs the repository's `post-checkout` hook. This is the same exposure as a shell prompt that runs `git status`; Maestro does not yet ask before running Git in a newly opened repository.

- Saving a file owned by another user keeps the permission bits but not the owner.
- A file with several hard links loses its link to the others when saved, because the save replaces the directory entry.
- Diagnostics published without a document version are placed on the current text. If the server computed them before your latest edit, they can land a few characters off until it publishes again. Versioned diagnostics for an older version are dropped.
- Ropey counts form feed, vertical tab, NEL and the Unicode line and paragraph separators as line breaks; the protocol counts only CR, LF and CRLF. A file containing those characters gets line numbers that disagree with the server's, and the server's copy of the text drifts after edits below them. Fixing it means building Ropey without its `unicode_lines` feature.
- A server that floods notifications can keep the editor busy: diagnostics are queued as jobs without a limit.
